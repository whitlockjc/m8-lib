# 6.6.x Research Plan

This is a developer plan, not a generated reference or a claim of 6.6.x
compatibility. The 6.5.x schema, fixtures, and generated reference remain
unchanged unless new evidence reveals an error that also applies to 6.5.x.

The initial 6.6.3C baselines and their observed headers are documented in
[the baseline inventory](research/6.6.x_BASELINE.md). The first controlled
edits and their byte mappings are in
[the targeted findings](research/6.6.x_TARGETED.md). The initial schema and
verification target are registered; broader compatibility research remains.

## Evidence To Collect

1. Record the exact firmware release and device for every fixture. Freshly
   created and older-file-then-resaved fixtures are separate experiments.
   Use `node tools/inspect-headers.js --inspect <file>` for new, unregistered
   releases; this reports bytes without asserting schema compatibility.
2. Create fresh baseline Song, Scale, Theme, and standalone Instrument files
   for every available instrument type. Inventory file kind, header schema
   version, byte length, and hashes. A matching header or length is not proof
   of a matching layout.
3. Compare baseline regions with 6.5.x by structure and repeated-record
   boundaries. A broad byte diff can include names, paths, timestamps, and
   persisted UI state, so classify changes before assigning meaning.
4. Repeat a small set of controlled 6.5.x edits on 6.6.x for each file kind.
   Check the beginning and end of repeated banks, plus standalone versus
   Song-embedded Instrument and Scale representations.
5. Create focused fixtures for the changelog's likely storage changes:
   Hypersynth Shape, ModFX Comb, and Song row bookmark colors/options.
   Investigate changed unknown regions related to the backend rework even
   where there is no new UI setting. Keep unverified interpretations explicit.

The [official changelog](https://github.com/Dirtywave/M8Firmware/blob/main/changelog.txt)
motivates the targeted fixtures; actual bytes determine the schema. A 6.6.x
manual or screenshots can help name fields, but cannot replace fixture evidence.

## Schema And Verification Decisions

- `schemas/6.6.x.ksy` now dispatches the observed file-header versions.
  Shared 6.5.x components are provisional where only baseline bytes have
  been compared; prioritize controlled edits before claiming full parity.
- New file-header versions use new `schemas/file-versions/<version>/` modules.
  If a layout or contextual enum changes without a header-version change,
  create a firmware-qualified variant and select it in the 6.6.x entry.
- Register 6.6.x in `tools/doc-targets.json` only when its entry schema, exact
  firmware provenance, fixture root, and distinct fixture/parsed checks exist.
- Registration makes `npm run verify` require 6.6.x to pass. The initial
  6.6.3C target now has three controlled fixture manifests and a distinct
  parsed-fixture suite; this verifies those fixtures, not every reused field.
- Generate `docs/6.6.x.md` from the entry. Shared components retain one
  generated page; changed components get pages matching their schema paths.
  Run both firmware suites and check that 6.5.x generated files do not drift.

## Completion Criteria

Every registered 6.6.x fixture passes header and parsed checks, controlled
changes are mapped or explicitly recorded as unknown, new UI values have
verified storage and contextual labels, cross-file embedded structures are
checked, and both firmware lines pass `npm run verify`. 6.6.x is not complete
merely because the Kaitai entry parses all four baselines. The initial target
is registered and passes; broader compatibility research remains open.

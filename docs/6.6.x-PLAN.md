# 6.6.x Research Plan

This is a developer plan, not a generated reference or a claim of 6.6.x
compatibility. The 6.5.x schema, fixtures, and generated reference remain
unchanged unless new evidence reveals an error that also applies to 6.5.x.

The initial 6.6.3C baselines and their observed headers are documented in
[the baseline inventory](research/6.6.x_BASELINE.md). The first controlled
edits and their byte mappings are in
[the targeted findings](research/6.6.x_TARGETED.md). The initial schema and
verification target are registered; broader compatibility research remains.

## Next Capture Sequence

The baseline set and controlled Shape, Comb, and bookmark fixtures already
exist. Extend that evidence with the batches below, one at a time. Suggested
filenames describe future captures; no fixture or manifest should be created
until the actual M8 files and their provenance are available. Confirm the exact
firmware and device first. If either differs from the existing capture setup,
record it and create a matching baseline; do not overwrite the committed
6.6.3C evidence or assume a different firmware range is compatible.

| Order | Experiment | Question answered |
| --- | --- | --- |
| 1 | Hypersynth Shape in Song slot `7F`, exported before and after one edit | Does the standalone Shape mapping also hold in the last embedded Instrument record? |
| 2 | Controlled Scale edits in Song slots `00` and `0F`, exported individually | Do embedded and standalone Scale records agree at both bank boundaries? |
| 3 | One Theme color component change | Does the shared Theme layout describe edited values as well as defaults? |
| 4 | Instrument parameters, modulation, and tables, captured as separate edits | Do reused Instrument layouts hold for nondefault settings across instrument types? |
| 5 | Song sequencing, MIDI, mixer/effects, and EQ edits, one structure per capture | Do reused Song layouts hold across their repeated banks and parameter groups? |

For batches 2–5, prepare the exact UI changes after the preceding batch has
been reviewed. Use existing 6.5.x experiments as templates, not as proof of
6.6.x behavior. A representative edit strengthens only the fields and
boundaries exercised; it does not establish full parity for a component.

### First Experiment: Embedded Hypersynth Shape

Capture status (2026-10-13): the four files have been imported and checked for
firmware 6.6.3C. The user loaded each corresponding export into Song slot `7F`
rather than changing Shape in place, so both Song and instrument names differ.
The complete embedded record and table match each standalone export; the
embedded Shape mapping is confirmed for this pair. Screenshots remain absent.
The byte-comparison checkpoint is complete;
see [the recorded findings](research/6.6.x_TARGETED.md#hypersynth-export-pair-2026-10-13).

1. Record the exact firmware release and device, with a firmware-screen
   screenshot. Start a fresh Song on that firmware rather than importing a
   6.5.x Song.
2. Set Instrument slot `7F` to Hypersynth. Leave its other parameters and
   table at their defaults. Capture the Instrument screen with slot, type,
   and Shape visible. Record the displayed default Shape rather than assuming
   it is SAW.
3. Save the baseline Song as `HYP_EMB_A.m8s` and export that slot as
   `HYP_EMB_A.m8i`. Record any name changes caused by saving or exporting.
4. Change only Shape to `0B` / SINE ORGAN. If that is already the default or
   the UI differs, record the state and revise the experiment before capture.
   Take a screenshot showing the modified setting.
5. Save the modified Song as `HYP_EMB_B.m8s` and export the same slot as
   `HYP_EMB_B.m8i`. Keep the baseline files intact. Record any unavoidable
   navigation, naming, or save-state changes.
6. Make the four files and screenshots available for inspection, along with
   the firmware/device details. Copy them into the firmware-specific fixture
   directories only after checking names for collisions and checking headers.

Analysis after capture:

- Inventory headers, sizes, and hashes. The existing 6.6.3C evidence predicts
  Instrument schema `6.0.2` and Song schema `6.6.2`; treat deviations as new
  evidence requiring review.
- Diff each before/after pair and account for every changed byte. Separate
  name and incidental save-state changes from Shape changes; document any
  ignored ranges rather than discarding them silently.
- Compare the exported Instrument's 215-byte record with Song Instrument
  `7F`, and its 128-byte table with Song table `7F`. The header and appended
  standalone table are outside the 215-byte record. Report name/state
  differences explicitly instead of assuming whole-record equality.
- Test the existing prediction that Shape occupies record-relative `0x2b`
  (standalone file offset `0x39`). Locate the embedded record from the current
  Song schema and byte evidence; do not treat the prediction as a finding.
- Add a manifest and targeted parsed-fixture assertions for the actual
  findings, then run `npm run verify` for both firmware targets. Change schemas
  only if the new evidence warrants it, and regenerate references if needed.

## Evidence To Collect

Scale batch status (2026-10-13): `SCALE_A/B.m8n` and `SCALE_A/B.m8s`
confirm the 440.00 to 441.00 Hz tuning-offset change and full standalone/body
equality for embedded slot `00`. Screenshots were omitted by user choice.
Slot `0F` remains uncaptured; nondefault intervals and enabled-note changes
are outside this experiment. See
[the Scale findings](research/6.6.x_TARGETED.md#scale-slot-00-tuning-2026-10-13).

1. Record the exact firmware release and device for every fixture. Freshly
   created and older-file-then-resaved fixtures are separate experiments.
   Use `node tools/inspect-headers.js --inspect <file>` for new, unregistered
   releases; this reports bytes without asserting schema compatibility.
2. Create fresh baseline Song, Scale, Theme, and standalone Instrument files
   for every available instrument type. Inventory file kind, header schema
   version, byte length, and hashes. A matching header or length is not proof
   of a matching layout.
3. Compare baseline regions with 6.5.x by structure and repeated-record
   boundaries. A broad byte diff can include names, paths, timestamps, and
   persisted UI state, so classify changes before assigning meaning.
4. Repeat a small set of controlled 6.5.x edits on 6.6.x for each file kind.
   Check the beginning and end of repeated banks, plus standalone versus
   Song-embedded Instrument and Scale representations.
5. Create focused fixtures for the changelog's likely storage changes:
   Hypersynth Shape, ModFX Comb, and Song row bookmark colors/options.
   Investigate changed unknown regions related to the backend rework even
   where there is no new UI setting. Keep unverified interpretations explicit.

The [official changelog](https://github.com/Dirtywave/M8Firmware/blob/main/changelog.txt)
motivates the targeted fixtures; actual bytes determine the schema. A 6.6.x
manual or screenshots can help name fields, but cannot replace fixture evidence.

## Schema And Verification Decisions

- `schemas/6.6.x.ksy` now dispatches the observed file-header versions.
  Shared 6.5.x components are provisional where only baseline bytes have
  been compared; prioritize controlled edits before claiming full parity.
- New file-header versions use new `schemas/file-versions/<version>/` modules.
  If a layout or contextual enum changes without a header-version change,
  create a firmware-qualified variant and select it in the 6.6.x entry.
- Register 6.6.x in `tools/doc-targets.json` only when its entry schema, exact
  firmware provenance, fixture root, and distinct fixture/parsed checks exist.
- Registration makes `npm run verify` require 6.6.x to pass. The initial
  6.6.3C target now has seven controlled fixture manifests and a distinct
  parsed-fixture suite; this verifies those fixtures, not every reused field.
- Generate `docs/6.6.x.md` from the entry. Shared components retain one
  generated page; changed components get pages matching their schema paths.
  Run both firmware suites and check that 6.5.x generated files do not drift.

## Completion Criteria

Every registered 6.6.x fixture passes header and parsed checks, controlled
changes are mapped or explicitly recorded as unknown, new UI values have
verified storage and contextual labels, cross-file embedded structures are
checked, and both firmware lines pass `npm run verify`. 6.6.x is not complete
merely because the Kaitai entry parses all four baselines. The initial target
is registered and passes; broader compatibility research remains open.

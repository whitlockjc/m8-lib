# 6.6.x Targeted Fixture Findings

Fixtures were created with M8 firmware **6.6.3C** and compared against the
fresh 6.6.x defaults in `fixtures/6.6.x/`. This is research evidence, not yet
an exhaustive 6.6.x compatibility claim. Offsets below are absolute
file offsets. The source files on the mounted SD card and the copied fixtures
had matching SHA-256 hashes.

## Hypersynth Shape

`instruments/HYP_SHAPE.m8i` has file schema version `6.0.2`. Relative to
`HYP_DEFAULT.m8i`, the name changes and exactly one other byte changes:

| Field | Offset | Default | Modified |
| --- | ---: | ---: | ---: |
| Hypersynth shape | `0x39` | `0x00` | `0x0b` |

This locates the Shape parameter in the standalone Instrument record. The
6.5.x Hypersynth default has `0xff` at this offset, inside a region currently
classified as unknown. Do not backport Shape to 6.5.x based on this fixture.

The supplied 6.6.x UI labels are: `00` SAW, `01` SOFT SAW, `02` DARK SAW,
`03` SQUARE SOFT, `04` TRIANGLE, `05` SINE, `06` SINE 3X, `07` SINE FB,
`08` SINE FOLD, `09` SINE RING, `0A` SINE HALF, `0B` SINE ORGAN. This fixture
directly verifies the stored values `00` and `0B`; the intermediate labels
come from the user's UI enumeration.

## ModFX Comb

`songs/MODFX_COMB.m8s` has Song file schema version `6.6.2`. Apart from the
directory/save-state bytes and the project name, one Song data byte changes:

| Field | Offset | Default | Modified |
| --- | ---: | ---: | ---: |
| ModFX type | `0x1a5da` | `0x00` | `0x03` |

This is the ModFX type location already mapped in 6.5.x, where `00` is
CHORUS. The controlled fixture establishes `03` as COMB for 6.6.x. It does
not by itself prove every other Effects field is unchanged.

## Bookmarks

`songs/BOOKMARKS.m8s` has Song file schema version `6.6.2`. The chain-cell
bookmark bytes are unchanged in layout from the known 6.5.x bitmask field:

| Row | Offset | Track mask | Selected tracks |
| --- | ---: | ---: | --- |
| `00` | `0x1a97e` | `0x55` | 1, 3, 5, 7 |
| `01` | `0x1a97f` | `0xaa` | 2, 4, 6, 8 |
| `fe` | `0x1aa7c` | `0x55` | 1, 3, 5, 7 |
| `ff` | `0x1aa7d` | `0xaa` | 2, 4, 6, 8 |

The 256-byte region newly appended to the 6.6.x Song begins at `0x1b6c6`.
The selected row-color values are at `0x1b6c6 + row index`; all unselected
entries remain zero in this fixture.

of the other possible byte values has not been tested. The chain bitmask and
row color are independent regions, so a row can carry both kinds of bookmark.

## Unrelated Changed Bytes

Both modified Songs also change their project names and bytes within the
128-byte directory field, including bytes after the path terminator. The
Project record's unknown trailing state at `0xbd..0xbe` also changes. These
are not assigned to Shape, ModFX, or bookmarks. As with 6.5.x fixtures, the
directory's post-terminator bytes must be preserved rather than interpreted
as stable zero padding.

## Hypersynth Export Pair: 2026-10-13

The user reports firmware **6.6.3C**. `HYP_EMB_A.m8i` and `HYP_EMB_B.m8i`
were copied unchanged from `/Volumes/M8Headless/Instruments/6_6_X/` into
`fixtures/6.6.x/instruments/`. Both carry Instrument schema version `6.0.2`
and are 357 bytes. Source and destination SHA-256 hashes match:

| File | SHA-256 |
| --- | --- |
| `HYP_EMB_A.m8i` | `ba18b33cc8c72e98e1a8aa33ca037e36b549be6aa77463394851a4ca1be41437` |
| `HYP_EMB_B.m8i` | `00989f10bc2f65212cb7d44f88fa1e0d0ebf174dd51b85d636ffec0f1e0b76c7` |

Exactly two bytes differ: the name suffix at `0x17` changes from `0x41`
(`A`) to `0x42` (`B`), and Shape at `0x39` changes from `0x00` to `0x0b`.
All other bytes, including the appended table, match. The pair corroborates
the existing standalone Shape mapping; no schema change is needed.

The user subsequently created the matching Songs on 6.6.3C by loading each
corresponding instrument export into slot `7F`, so both the Song name and
embedded instrument name match the A/B suffix. This differs from changing Shape
in place in a single Song. Screenshots have not been supplied; no new UI label
evidence is claimed.

### Matching Song Evidence

The Songs were copied unchanged from `/Volumes/M8Headless/Songs/6_6_X/` into
`fixtures/6.6.x/songs/`. Both have file schema `6.6.2` and size 112582 bytes.
Source and destination SHA-256 hashes match:

| File | SHA-256 |
| --- | --- |
| `HYP_EMB_A.m8s` | `c1ff3b8da3376edba32629bea5fba871008e42aba6bd1e69cda4ada7b9d84d7a` |
| `HYP_EMB_B.m8s` | `9ed74cdab3ab214f81c72b24b51318fa52b4711ab1df9007f1e15acab49499dc` |

Exactly four Song bytes differ:

| Field | Absolute offset | A | B |
| --- | --- | --- | --- |
| Project name suffix | `0x009c` | `0x41` | `0x42` |
| Preserved unknown Project state | `0x00bd` | `0x4a` | `0x25` |
| Instrument `7F` name suffix | `0x1a4f0` | `0x41` | `0x42` |
| Instrument `7F` Shape | `0x1a512` | `0x00` | `0x0b` |

For each A/B pair, all 215 bytes of the Song instrument record at
`0x1a4e7..0x1a5bd` equal the standalone record at `0x0e..0xe4`, including its
name and preserved bytes. All 128 bytes of Song table `7F` at
`0xf9be..0xfa3d` equal the standalone table at `0xe5..0x164`. These tables
are unchanged between A and B; equality does not verify nondefault table edits.

Shape is therefore at record-relative `0x2b` in both representations:
`0x39` standalone and `0x1a512` in Song slot `7F`. The existing schemas agree;
no schema changes are needed. The manifest accounts for the three deliberate
name/Shape changes and separately ignores the one unknown state byte. Its
meaning remains unspecified. Verification checks decoded names and Shape,
record and table equality, and the complete set of changed offsets.

## Scale Slot 00 Tuning: 2026-10-13

Firmware is user-reported **6.6.3C**. The user supplied the requested baseline
and modified pairs for Scale slot `00`, with a 440.00 to 441.00 Hz tuning edit.
Screenshots were intentionally omitted, so the requested UI values are capture
context rather than independently inspected screen evidence.

Files were copied unchanged from `/Volumes/M8Headless/Scales/6_6_X/` and
`/Volumes/M8Headless/Songs/6_6_X/` to their corresponding fixture directories.
Scales have schema version `4.0.1` and size 60 bytes; Songs have schema version
`6.6.2` and size 112582 bytes. Source/destination hashes match:

| File | SHA-256 |
| --- | --- |
| `SCALE_A.m8n` | `09af55f6900d1a80e83a3202ff1ac6ecc528c83da5e9bbe326b53a4c5fe0cc3c` |
| `SCALE_B.m8n` | `df585a8eb8c8990bbf6de1280b70fae37b87c2940aed787dc297393de5fc5b95` |
| `SCALE_A.m8s` | `239e32de29f20633ad99e3b1da93d110cc53567d8c5e16f14c0428b63b212d88` |
| `SCALE_B.m8s` | `fc6588fe49f9a0988fe5e0f0e1b6a84a721f4eb730959c3f39dac250b33a969a` |

Standalone A/B files differ only at the name suffix (`0x2e`, `41 -> 42`)
and the four-byte tuning field (`0x38..0x3b`, `00 00 00 00 -> 00 00 80 3f`).
Only two tuning bytes actually change. The existing schema decodes the field
as little-endian float 0.0 -> 1.0 Hz offset from A440.

Song differences are the Project name suffix at `0x9a`, Scale name suffix at
`0x1aa9e`, tuning at `0x1aaa8..0x1aaab`, and unknown Project state at `0xbd`
(`49 -> 3c`). The latter is recorded separately with no semantic assignment.
All five changed Song bytes are accounted for by the manifest.

For both A and B, the complete 46-byte standalone body (`0x0e..0x3b`) equals
Song Scale `00` (`0x1aa7e..0x1aaab`), including name padding, enabled notes,
intervals, and tuning. The existing shared Scale schema describes this edit
correctly; no schema changes are needed. Verification checks raw record equality,
decoded fields, and the full changed-byte sets. This pair covers slot `00`
and tuning only; nondefault intervals, enabled notes, and slot `0F` remain
outside this experiment.

## Remaining Work

- The 6.6.2 Song and 6.0.2 Instrument schema components now model these
  findings. Do not modify the 6.5.x components for new fields.
- Extend embedded Instrument coverage beyond this Hypersynth pair, and repeat
  targeted edits on Scale and other shared
  structures before asserting full 6.6.x semantic compatibility.
- Investigate `0xbd..0xbe` separately if its meaning is needed.
- The initial 6.6.x parsed-fixture suite and generated `docs/6.6.x.md` now
  cover the supplied evidence. Expand them as new fixtures arrive.
